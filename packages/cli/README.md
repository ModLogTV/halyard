# @modlogtv/halyard-cli

The command line tool of Halyard, the self-hosted feature flag platform. It generates TypeScript types from your flags and imports and exports whole projects, so flags can live in CI and in version control.

- **Typed flags.** `halyard types` turns your flag definitions into a TypeScript module: flag keys, value types, variant keys, code defaults and a typed OpenFeature client interface.
- **Import / export.** Move a project between instances, or keep it in git, with a readable diff before anything is changed.
- **CI friendly.** Credentials from environment variables, machine-readable output with `--json`, and stable exit codes.
- **No runtime dependencies.** Node 20 or newer, or Bun.

## Install

```sh
# as a dev dependency (recommended: pins the version for your team and CI)
npm i -D @modlogtv/halyard-cli
bun add -d @modlogtv/halyard-cli

# or run it without installing
bunx @modlogtv/halyard-cli --help
npx @modlogtv/halyard-cli --help
```

The binary is called `halyard`. Examples below assume it is on your path (`npx halyard …` / `bunx halyard …` / a package script).

## Log in

Create a **management key** in your Halyard instance (Settings → API keys; keys start with `hal_mgmt_`). `types` and `export` work with any management key; applying an import needs a key with write access.

```sh
halyard login --url https://flags.example.com --key hal_mgmt_…
```

Without `--url` / `--key` the command asks for them (the key is not echoed). The key can also be piped, which keeps it out of your shell history and process list:

```sh
echo "$HALYARD_KEY" | halyard login --url https://flags.example.com
```

`login` verifies the key with `GET /api/v1/projects/current`, prints the project name, and stores `{ url, key }` in a config file with mode `0600`:

| Platform | Config file |
| --- | --- |
| Linux, macOS | `$XDG_CONFIG_HOME/halyard/config.json`, default `~/.config/halyard/config.json` |
| Windows | `%APPDATA%\halyard\config.json` |

Use profiles for several instances or projects:

```sh
halyard login --profile staging --url https://staging.flags.example.com
halyard whoami --profile staging
halyard logout --profile staging
```

`halyard whoami` shows which project the current credentials belong to (`--json` for scripts). `halyard logout` removes a profile.

### How credentials are resolved

For every command, each value is taken from the first source that has it:

1. flags: `--url`, `--key`, `--profile`
2. environment: `HALYARD_URL`, `HALYARD_API_KEY`, `HALYARD_PROFILE`
3. the profile in the config file (`default` unless selected)

A stored key is never sent to a different URL than the one it was stored for: `--url https://other` without `--key` is an error rather than a leak. `--key -` reads the key from stdin.

## Generate types

```sh
halyard types --out src/flags.generated.ts
```

| Option | Description |
| --- | --- |
| `--out <file>` | Write to a file (parent directories are created). Default: stdout. |
| `--namespace <Name>` | Wrap everything in `export namespace <Name> { … }`. |
| `--include-archived` | Include archived flags (excluded by default). |

The output is deterministic (flags sorted by key) apart from the timestamp in the header. Example:

```ts
// Generated by @modlogtv/halyard-cli — do not edit by hand.
// Project: acme · 3 flags · 2026-01-02T03:04:05.000Z

/** All flag keys of the project. */
export const flagKeys = ['checkout.new-payment-flow', 'pricing.plan-banner', 'search.results-per-page'] as const

export type FlagKey = (typeof flagKeys)[number]

/** The value type of every flag. String and number flags are unions of their variant values. */
export interface Flags {
  /** New payment flow — Replaces the legacy checkout. */
  'checkout.new-payment-flow': boolean
  /** Pricing page banner */
  'pricing.plan-banner': 'none' | 'Save 20% with annual billing'
  'search.results-per-page': 10 | 25 | 50
}

export type FlagValue<K extends FlagKey> = Flags[K]

/** Variant keys per flag. */
export interface FlagVariants { … }

/** Code defaults: the value of each flag's first variant. Override as needed. */
export const flagDefaults: { [K in FlagKey]: Flags[K] } = { … }

/** Typed wrapper for an OpenFeature client. */
export interface TypedFlagClient { … }
export type BooleanFlagKey = 'checkout.new-payment-flow'
export type StringFlagKey = 'pricing.plan-banner'
export type NumberFlagKey = 'search.results-per-page'
export type JsonFlagKey = never
```

How flags are typed:

- `boolean` flags are `boolean`.
- `string` and `number` flags are unions of their variant values (deduplicated, in variant order).
- `json` flags get a structural type inferred from their variant values: objects become `{ key: type }`, strings, numbers and booleans are widened to `string`, `number` and `boolean`, arrays become `T[]` (`unknown[]` when empty), `null` stays `null`, and the distinct variant types are joined into a union.
- Keys that are not valid identifiers are quoted; names and descriptions become doc comments.

`TypedFlagClient` has no dependency on OpenFeature. Any OpenFeature client satisfies it structurally, so you can narrow one with a cast:

```ts
import { OpenFeature } from '@openfeature/server-sdk'
import type { TypedFlagClient } from './flags.generated'

const flags = OpenFeature.getClient() as unknown as TypedFlagClient

const enabled = await flags.getBooleanValue('checkout.new-payment-flow', false)
const perPage = await flags.getNumberValue('search.results-per-page', 25) // 10 | 25 | 50
// flags.getBooleanValue('does-not-exist', false)   // compile error
```

### In CI

Regenerate on every build, or check that the committed file is current:

```yaml
# .github/workflows/ci.yml
- run: npx halyard types --out src/flags.generated.ts
  env:
    HALYARD_URL: ${{ vars.HALYARD_URL }}
    HALYARD_API_KEY: ${{ secrets.HALYARD_API_KEY }}
- run: git diff --exit-code -I'^// Project:' src/flags.generated.ts
```

The `-I` ignores the header line with the timestamp. As a package script: `"flags": "halyard types --out src/flags.generated.ts"`.

## Export

```sh
halyard export --out halyard.json                # the full project, as JSON
halyard export --format flagd --environment production --out flags.flagd.json
```

| Option | Description |
| --- | --- |
| `--out <file>` | Write to a file. Default: stdout. |
| `--format json\|flagd` | `json` (default) is the Halyard export document. `flagd` is a [flagd](https://flagd.dev) flag file for one environment. |
| `--environment <key>` | Environment to export. Required with `--format flagd`. |
| `--json` | Accepted for scripts; the output is JSON anyway. |

The JSON document contains environments, segments, and every flag with its variants and per-environment targeting. It is meant to be committed to git and restored with `halyard import`. Warnings (for example features flagd cannot express) are printed to stderr in yellow.

## Import

```sh
halyard import halyard.json --dry-run      # show what would change
halyard import halyard.json                # show the diff, ask, apply
halyard import halyard.json --prune --yes  # CI: delete what is not in the file
```

| Option | Description |
| --- | --- |
| `--dry-run` | Only print the diff, change nothing. |
| `--prune` | Delete environments, segments and flags that are not in the document. |
| `--yes`, `-y` | Apply without asking. Required when stdin is not a terminal. |
| `--json` | Print the server response as JSON instead of the readable diff. |

`<file>` can be `-` to read the document from stdin (then `--yes` is required).

The command always sends a dry run first and prints the result per section (environments, segments, flags):

```
Flags
  + new-flag  (New flag)
  ~ checkout.new-payment-flow
      description: null → "Faster checkout"
      [production]
        enabled: false → true
  - old-flag
  = 12 unchanged

1 to create, 1 to update, 1 to delete, 12 unchanged
```

`+` is created, `~` updated (with field changes, per environment where applicable), `-` deleted. Validation errors are printed in red and abort the import with exit code 1; warnings are yellow. Unless you passed `--dry-run`, it then asks `Apply these changes? (y/N)` and applies the document. Without a terminal it refuses to apply unless `--yes` is given. With `--json`, nothing but the final JSON response is written to stdout (`--yes` is required to apply).

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success (including a dry run and "nothing to import"). |
| `1` | Validation errors from the server, invalid input or usage, import declined or missing `--yes`. |
| `2` | Configuration or authentication problem: not logged in, invalid key (401), key without write access (403), URL that is not a Halyard instance. |
| `3` | Network error: connection refused, DNS failure, TLS error, timeout (30 s), or a 5xx from the server. |

Errors are written to stderr as `error: <message>`, with a hint where there is one. Set `HALYARD_DEBUG=1` to get stack traces for unexpected errors.

## Command reference

```
halyard login   [--url <url>] [--key <key>] [--profile <name>]
halyard logout  [--profile <name>]
halyard whoami  [--json]
halyard types   [--out <file>] [--namespace <Name>] [--include-archived]
halyard export  [--out <file>] [--format json|flagd] [--environment <key>] [--json]
halyard import  <file> [--prune] [--dry-run] [--yes] [--json]
```

Every command except `login` and `logout` also accepts `--url`, `--key` and `--profile`. All commands accept `--no-color` (also: `NO_COLOR`; `FORCE_COLOR` forces colour on), `--help`; `halyard --version` prints the version.
